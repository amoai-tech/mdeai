## Real-world problem
Ask the MDE concierge on WhatsApp for *"a furnished 2-bedroom in Laureles under COP 3.5 million per month"* and you get a summary — because the agent is correctly told not to repeat card fields in prose (the **web** CopilotKit cards render them). WhatsApp has no cards, so the customer sees no prices and no links. The search results are real; the channel just never writes them out.

## What changed
- **`src/mastra/tools/whatsapp-rental-reply.ts`** (new): deterministic formatter built from the **same** `searchRentalsTool` results — title, neighborhood, the listing's own monthly price, bedrooms, verified furnished/amenities, and a validated `http(s)` link; a viewing link only when `can_schedule_viewing` is true. Other-currency listings appear in a separate block and are **never** labelled as within the budget. Unknown prices render as "price on request".
- **`search-rentals.ts`**: returns `whatsapp_reply` **only** on WhatsApp runs (`isWhatsAppRun` reads the channel render context on the run's RequestContext), and `monthlyBudgetFromQuery` feeds the formatter. Web output is unchanged.
- **`concierge.ts`**: when a tool result carries `whatsapp_reply`, send it verbatim; call `search-rentals` with `maxPriceMonthly`/`budgetCurrency` for monthly budgets; never convert currencies.

No new agent, table, index or search path.

## Tests
**26 passing** (`vitest run src/mastra/tools/__tests__/whatsapp-rental-reply.test.ts rental-monthly-budget.test.ts`): real titles/prices/amenities/links, three-option cap, other-currency separation, unknown price not invented, malformed URL dropped, unauthorized viewing never offered, requestable viewing link offered, and the same-currency budget rules. `tsc`, `eslint src --max-warnings 0` clean.

## ⚠️ Not yet proven end-to-end (important)
The real-agent E2E ran (local Supabase + isolated Meta endpoint): inbound accepted, row `processed`, **1** physical send — but the agent answered *"No 2-bedroom rentals were found…"*. The tool executed twice with `status: 'ok'`; two eligible COP rows existed and passed a **service-role** query, but the app's **RLS-scoped** client returned nothing. So the run did not demonstrate a grounded WhatsApp answer, and I could not confirm the model relays `whatsapp_reply`.

**I am not claiming the customer journey works.** Before this ships the E2E must be made to return real listings through the app's RLS path (diagnose the seed shape vs the public eligibility policy), then assert the sent message contains a real title, a COP monthly price and a working link. `isWhatsAppRun` also reads an `@internal` Mastra key (`__mastra_chat_channel_render`); if that shape drifts, the tool silently stops emitting `whatsapp_reply` — the E2E is what would catch it.

## Safety
WhatsApp remains disabled (webhook 503 / POST-only 405); no production traffic, no data writes beyond local test rows that were cleaned up (0 residual).
