[SAN-1444 · MDE WhatsApp — Prove Signed Meta Webhook and Mastra Concierge Round Trip](https://linear.app/amo100/issue/SAN-1444/mde-whatsapp-prove-signed-meta-webhook-and-mastra-concierge-round-trip)

## Real-world problem
The webhook acknowledged Meta before anything recoverable was written, so a crash could lose a customer message and a redelivery could start the concierge twice.

## What changed (after the production-readiness audit)
- **Record before acknowledging.** Every inbound message is written with `whatsapp_record_inbound` first; a failed write returns **500** so Meta retries. 200 only after commit.
- **Atomic claim + fencing.** `whatsapp_claim_inbound` sets a fresh `claim_token`; complete/fail carry it and update only while that claim owns the row, returning the affected-row count. A fenced-out worker is reported **stale**, never counted as success.
- **Completion follows real processing.** The adapter receives `waitUntil` and the worker awaits that promise (bounded, 150s) before marking processed. **An HTTP 200 from the webhook is not treated as proof the customer received an answer.**
- **Bounded retries everywhere.** The attempt ceiling applies to the lease-expiry path too; exhausted work is **dead-lettered**.
- **Correct replay metadata.** A single-message envelope is built from the message's **own entry and change**, so batch payloads replay correctly.
- **Scheduled recovery.** `sq/migrations/…recovery_schedule.sql` runs the sweeper every 2 minutes via pg_cron/pg_net, using Vault secrets `mde_app_url` and `whatsapp_process_secret` (missing secret raises rather than guessing a host).
- **Deduplication** reuses the existing `whatsapp_messages.external_id` index — no new messages table.
