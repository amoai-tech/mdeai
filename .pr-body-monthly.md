## Real-world problem
A renter asking for **"a furnished 2-bedroom in Laureles under COP 3.5 million per month"** could not be filtered. The only budget input was `maxPricePerNight` (USD per night), and a COP monthly listing was deliberately **retained without comparison** — so a COP 4.0M/month flat could sit in the results beside a COP 2.9M one, with no way to tell the budget was applied. Converting COP to a USD nightly cap would invent an exchange rate, which this repository has no source for.

## What changed
A canonical **same-currency monthly budget**:
- `RentalQuery.maxPriceMonthly` + `budgetCurrency` (default `COP`), exposed on `searchRentalsTool` so the concierge can pass them.
- `rentalMonthlyBudgetPredicate(amount, currency)` applies the ceiling **only** to listings in that currency with a stored `price_monthly`; other-currency listings are retained and never compared. A COP nightly-only row is never presented as a monthly match.
- `rentalBudgetPredicate(...)` is now the single entry point used by **both** search paths (`search-rentals.ts` and `intelligence-rental-search.ts`), so they cannot disagree.
- `budgetNoteFor(query)` tells the model the monthly contract instead of the nightly one.

No new agent, search engine, table, index, or query — same tool, one added predicate.

## Honest scope
This PR makes the **filter** correct and usable. The WhatsApp reply still shows the web-shaped answer, so a **channel-aware formatting layer** (2–3 grounded options with COP monthly prices and validated links) is the next, separate PR — the two must be tested together before the customer journey is called done. The concierge is not yet told, in its instructions, to pass `maxPriceMonthly` for a COP monthly budget; the tool schema documents it, and the follow-up formatting PR should wire the instruction.
